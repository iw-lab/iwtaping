⑥의 기준은 **일반적인 게임 원리에서 배우고 구체적인 표현은 직접 제작하는 것**입니다. 게임 아이디어·플레이 방법과 문학적·시각적 표현은 구분됩니다. 이는 [미국 저작권청의 게임 안내](https://www.copyright.gov/register/tx-games.html)에도 설명되어 있습니다. 표는 개별 작품의 이용 허락을 뜻하지 않으며, 이름·로고는 상표 문제도 별도로 고려해야 합니다.

**3D에서 글자 가독성을 지키는 설계 규칙 7개**입니다. 수치는 이번 프로젝트의 초기 제안값이며, 초등학생 대상 실측 결과는 아닙니다.

1. **입력할 글자는 화면과 평행하게 유지합니다.** 대상의 3D 위치를 화면 좌표로 투영해 평면 라벨을 붙이고, 현재 단어와 입력칸은 고정 HUD에도 표시합니다. 회전하는 물체 표면에 필수 단어를 직접 새기지 않습니다.

2. **글자 크기는 거리보다 화면상의 크기로 관리합니다.** 한글·영문 모두 우선 **24~32 CSS px**로 시험합니다. 먼 대상도 최소 크기를 유지하고, 긴 단어는 라벨 폭을 늘립니다. 빌보드는 방향만 맞춰주므로 원근에 따른 축소는 별도로 처리해야 합니다.

3. **글자 뒤에 안정적인 바탕을 둡니다.** 단색에 가까운 패널과 충분한 여백을 사용합니다. 배경 조명·안개·블룸·피격 섬광이 글자의 색과 선명도를 바꾸지 않게 하고, 정답·오답은 색과 밑줄·기호를 함께 사용합니다.

4. **동시 표시량과 겹침을 제한합니다.** 처음에는 읽어야 할 단어를 **4~6개**로 제한합니다. 라벨의 화면 사각형이 겹치면 위치나 생성 시점을 조정하고, 연결선으로 대상을 구분합니다. 벽 뒤 대상의 라벨은 숨기되 현재 입력 단어는 HUD에서 유지합니다.

5. **읽는 동안 카메라와 표적을 안정시킵니다.** 급회전·자동 줌·머리 흔들림을 기본적으로 끕니다. 입력을 시작하면 표적을 고정하고, 같은 첫 글자가 있는 단어들의 선택 순서도 일관되게 정합니다.

6. **타격 효과는 글자를 가리지 않는 위치에 배치합니다.** 작은 입력 반응은 즉시 주고, 큰 보상은 단어 완성 뒤 대상 주변에서 재생합니다. 필수 단어에는 모션 블러·잔상·왜곡을 적용하지 않으며, 화면 흔들림과 섬광을 줄이는 옵션을 제공합니다.

7. **한글 조합 상태를 읽을 수 있게 보여줍니다.** 실제 HTML 입력 요소를 사용하고, `ㅎ→하→한` 같은 조합 중 글자를 오타로 벌점 처리하지 않습니다. 조합 중 표적을 바꾸지 않고, 확정값은 한 번만 반영합니다. 영어는 확정된 글자 진행, 한글은 확정 음절과 조합 중 부분을 구분합니다. 조합 종료 이벤트는 [브라우저 입력 이벤트](https://developer.mozilla.org/en-US/docs/Web/API/Element/compositionend_event)로 처리할 수 있습니다.

HTML 라벨은 한글 폰트와 크기 관리에 유리합니다. 다만 Three.js의 `CSS2DRenderer`는 공식 문서상 브라우저·디스플레이 확대율 100%만 지원하므로, 학교의 확대 설정을 지원하려면 실제 환경에서 확인하거나 별도 DOM 오버레이 좌표 처리를 설계해야 합니다. [CSS2DRenderer 문서](https://threejs.org/docs/pages/CSS2DRenderer.html)

**저사양 학교 PC에서 60fps를 목표로 하는 Three.js 규칙 7개**입니다. 내장 GPU·크롬북의 성능 차이가 크므로, 이 규칙만으로 60fps를 보장할 수는 없습니다.

1. **실제 기기에서 프레임 예산을 정합니다.** 60fps의 프레임 간격은 약 16.7ms입니다. 가장 느린 학교 기기에서 최대 적·라벨·효과가 겹치는 상황을 측정하고, 평균 FPS와 함께 프레임 간격의 95백분위·긴 프레임 발생도 기록합니다. `renderer.info`로 드로 콜·삼각형·텍스처 수를 추적합니다. [WebGLRenderer 문서](https://threejs.org/docs/pages/WebGLRenderer.html)

2. **렌더 해상도를 제한합니다.** 우선 DPR 상한 1, 약 1280×720 수준에서 시험합니다. 지속적으로 느리면 3D 캔버스 해상도부터 낮추고 HTML 글자는 선명하게 유지합니다. 매 프레임 해상도를 바꾸지 않도록 품질 전환에 여유 구간을 둡니다. [해상도 관련 API](https://threejs.org/docs/pages/WebGLRenderer.html#setDrawingBufferSize)

3. **반복 물체는 묶어서 그립니다.** 빗방울·적·타일·별은 같은 지오메트리와 재질을 공유하고 `InstancedMesh`를 활용합니다. 정적인 배경은 가능한 범위에서 병합합니다. 초기 장면 예산은 **드로 콜 50 이하·표시 삼각형 10만 이하**로 잡고 실측으로 조정합니다. 이 수치는 보장 기준이 아닙니다. [InstancedMesh 문서](https://threejs.org/docs/pages/InstancedMesh.html)

4. **조명과 그림자는 단순하게 시작합니다.** 기본 조명 소수와 단순 재질을 사용하고, 바닥 접촉 그림자는 둥근 이미지나 베이크로 표현합니다. 실시간 그림자·반사·투명 굴절·전체 화면 후처리는 낮은 품질 설정에서 끕니다.

5. **글자 생성과 DOM 갱신 비용을 제한합니다.** 타건마다 `TextGeometry`나 텍스처를 새로 만들지 않습니다. 소수의 HTML 라벨을 재사용하고, 위치는 CSS transform으로 갱신하며, 내용·색상은 실제 입력이 바뀔 때만 수정합니다. 매 프레임 레이아웃 크기를 다시 읽지 않습니다.

6. **효과와 게임 로직에 상한을 둡니다.** 적·파티클·오디오를 풀링하고 동시 개수를 제한합니다. 단순 레인 게임은 무거운 물리 엔진 대신 좌표와 경계 비교로 처리합니다. 매 프레임 임시 객체·전체 UI 재렌더를 줄이고, 탭 복귀 시 큰 시간 차이로 객체가 순간이동하지 않게 합니다.

7. **플레이 전 준비하고 전환 후 정리합니다.** 모델·폰트·효과음을 미리 준비하고, 가능하면 `compileAsync()`로 셰이더를 사전 컴파일합니다. 장면을 버릴 때 사용이 끝난 지오메트리·재질·텍스처를 해제합니다. 현재 `WebGLRenderer`는 WebGL 2가 필요하므로 시작 시 지원 여부를 확인하고, 사용할 수 없는 기기에는 기존 2D 모드를 제공합니다. [WebGLRenderer 문서](https://threejs.org/docs/pages/WebGLRenderer.html)

⑥의 기준은 **일반적인 게임 원리에서 배우고 구체적인 표현은 직접 제작하는 것**입니다. 게임 아이디어·플레이 방법과 문학적·시각적 표현은 구분됩니다. 이는 [미국 저작권청의 게임 안내](https://www.copyright.gov/register/tx-games.html)에도 설명되어 있습니다. 표는 개별 작품의 이용 허락을 뜻하지 않으며, 이름·로고는 상표 문제도 별도로 고려해야 합니다.

**3D에서 글자 가독성을 지키는 설계 규칙 7개**입니다. 수치는 이번 프로젝트의 초기 제안값이며, 초등학생 대상 실측 결과는 아닙니다.

1. **입력할 글자는 화면과 평행하게 유지합니다.** 대상의 3D 위치를 화면 좌표로 투영해 평면 라벨을 붙이고, 현재 단어와 입력칸은 고정 HUD에도 표시합니다. 회전하는 물체 표면에 필수 단어를 직접 새기지 않습니다.

2. **글자 크기는 거리보다 화면상의 크기로 관리합니다.** 한글·영문 모두 우선 **24~32 CSS px**로 시험합니다. 먼 대상도 최소 크기를 유지하고, 긴 단어는 라벨 폭을 늘립니다. 빌보드는 방향만 맞춰주므로 원근에 따른 축소는 별도로 처리해야 합니다.

3. **글자 뒤에 안정적인 바탕을 둡니다.** 단색에 가까운 패널과 충분한 여백을 사용합니다. 배경 조명·안개·블룸·피격 섬광이 글자의 색과 선명도를 바꾸지 않게 하고, 정답·오답은 색과 밑줄·기호를 함께 사용합니다.

4. **동시 표시량과 겹침을 제한합니다.** 처음에는 읽어야 할 단어를 **4~6개**로 제한합니다. 라벨의 화면 사각형이 겹치면 위치나 생성 시점을 조정하고, 연결선으로 대상을 구분합니다. 벽 뒤 대상의 라벨은 숨기되 현재 입력 단어는 HUD에서 유지합니다.

5. **읽는 동안 카메라와 표적을 안정시킵니다.** 급회전·자동 줌·머리 흔들림을 기본적으로 끕니다. 입력을 시작하면 표적을 고정하고, 같은 첫 글자가 있는 단어들의 선택 순서도 일관되게 정합니다.

6. **타격 효과는 글자를 가리지 않는 위치에 배치합니다.** 작은 입력 반응은 즉시 주고, 큰 보상은 단어 완성 뒤 대상 주변에서 재생합니다. 필수 단어에는 모션 블러·잔상·왜곡을 적용하지 않으며, 화면 흔들림과 섬광을 줄이는 옵션을 제공합니다.

7. **한글 조합 상태를 읽을 수 있게 보여줍니다.** 실제 HTML 입력 요소를 사용하고, `ㅎ→하→한` 같은 조합 중 글자를 오타로 벌점 처리하지 않습니다. 조합 중 표적을 바꾸지 않고, 확정값은 한 번만 반영합니다. 영어는 확정된 글자 진행, 한글은 확정 음절과 조합 중 부분을 구분합니다. 조합 종료 이벤트는 [브라우저 입력 이벤트](https://developer.mozilla.org/en-US/docs/Web/API/Element/compositionend_event)로 처리할 수 있습니다.

HTML 라벨은 한글 폰트와 크기 관리에 유리합니다. 다만 Three.js의 `CSS2DRenderer`는 공식 문서상 브라우저·디스플레이 확대율 100%만 지원하므로, 학교의 확대 설정을 지원하려면 실제 환경에서 확인하거나 별도 DOM 오버레이 좌표 처리를 설계해야 합니다. [CSS2DRenderer 문서](https://threejs.org/docs/pages/CSS2DRenderer.html)

**저사양 학교 PC에서 60fps를 목표로 하는 Three.js 규칙 7개**입니다. 내장 GPU·크롬북의 성능 차이가 크므로, 이 규칙만으로 60fps를 보장할 수는 없습니다.

1. **실제 기기에서 프레임 예산을 정합니다.** 60fps의 프레임 간격은 약 16.7ms입니다. 가장 느린 학교 기기에서 최대 적·라벨·효과가 겹치는 상황을 측정하고, 평균 FPS와 함께 프레임 간격의 95백분위·긴 프레임 발생도 기록합니다. `renderer.info`로 드로 콜·삼각형·텍스처 수를 추적합니다. [WebGLRenderer 문서](https://threejs.org/docs/pages/WebGLRenderer.html)

2. **렌더 해상도를 제한합니다.** 우선 DPR 상한 1, 약 1280×720 수준에서 시험합니다. 지속적으로 느리면 3D 캔버스 해상도부터 낮추고 HTML 글자는 선명하게 유지합니다. 매 프레임 해상도를 바꾸지 않도록 품질 전환에 여유 구간을 둡니다. [해상도 관련 API](https://threejs.org/docs/pages/WebGLRenderer.html#setDrawingBufferSize)

3. **반복 물체는 묶어서 그립니다.** 빗방울·적·타일·별은 같은 지오메트리와 재질을 공유하고 `InstancedMesh`를 활용합니다. 정적인 배경은 가능한 범위에서 병합합니다. 초기 장면 예산은 **드로 콜 50 이하·표시 삼각형 10만 이하**로 잡고 실측으로 조정합니다. 이 수치는 보장 기준이 아닙니다. [InstancedMesh 문서](https://threejs.org/docs/pages/InstancedMesh.html)

4. **조명과 그림자는 단순하게 시작합니다.** 기본 조명 소수와 단순 재질을 사용하고, 바닥 접촉 그림자는 둥근 이미지나 베이크로 표현합니다. 실시간 그림자·반사·투명 굴절·전체 화면 후처리는 낮은 품질 설정에서 끕니다.

5. **글자 생성과 DOM 갱신 비용을 제한합니다.** 타건마다 `TextGeometry`나 텍스처를 새로 만들지 않습니다. 소수의 HTML 라벨을 재사용하고, 위치는 CSS transform으로 갱신하며, 내용·색상은 실제 입력이 바뀔 때만 수정합니다. 매 프레임 레이아웃 크기를 다시 읽지 않습니다.

6. **효과와 게임 로직에 상한을 둡니다.** 적·파티클·오디오를 풀링하고 동시 개수를 제한합니다. 단순 레인 게임은 무거운 물리 엔진 대신 좌표와 경계 비교로 처리합니다. 매 프레임 임시 객체·전체 UI 재렌더를 줄이고, 탭 복귀 시 큰 시간 차이로 객체가 순간이동하지 않게 합니다.

7. **플레이 전 준비하고 전환 후 정리합니다.** 모델·폰트·효과음을 미리 준비하고, 가능하면 `compileAsync()`로 셰이더를 사전 컴파일합니다. 장면을 버릴 때 사용이 끝난 지오메트리·재질·텍스처를 해제합니다. 현재 `WebGLRenderer`는 WebGL 2가 필요하므로 시작 시 지원 여부를 확인하고, 사용할 수 없는 기기에는 기존 2D 모드를 제공합니다. [WebGLRenderer 문서](https://threejs.org/docs/pages/WebGLRenderer.html)

**한 종부터 시험한다면 ‘떨어지는 단어 비’를 권합니다.** 카메라·낙하 경로·표시 개수를 통제하기 쉬우면서도 캡슐의 회전, 바닥 그림자, 깊이 있는 배경, 꽃이 피는 보상으로 3D 전환의 효과를 보여줄 수 있습니다. 디펜스의 경로 탐색, 레이스의 추적 카메라, 슈팅의 조준, 좀비의 복잡한 애니메이션보다 구현 변수가 적다는 설계 판단입니다.

첫 시제품은 **고정 카메라·3개 레인·최대 6개 단어·동일한 읽기 깊이·HTML 라벨·실시간 그림자 없음**으로 제한합니다. 배경과 보상에는 깊이를 주고, 입력 대상이 카메라 쪽으로 급격히 다가오지는 않게 합니다.

기존 2D판과 같은 단어·낙하 속도로 비교해 다음을 확인하면 전환 여부를 결정할 근거가 생깁니다.

- **학습 경험:** 정확도와 완주율이 유지되면서 아이들이 보상과 진행 상태를 이해하는가.

이 비교 실험과 기기 성능 측정은 아직 수행하지 않았으며, 위 수치들은 시제품을 시작하기 위한 제안값입니다.
