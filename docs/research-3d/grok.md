⑴ 3D에서 글자 가독성을 지키는 설계 규칙 7개
빌보드 우선: 텍스트는 항상 카메라 정면(Sprite 또는 CSS2DRenderer / HTML overlay). 원근으로 기울어지지 않게. (Epistory·TypeSh!t 방식 추정)
최소 크기 보장: 화면 픽셀 기준 최소 높이(예: 24~32px) 이하로 작아지지 않게 스케일 보정. 거리 멀수록 크게.
고대비·굵은 폰트: 배경과 대비 높은 색(흰+검정 아웃라인), 굵은 sans-serif. 한글은 자소 분리 주의.
배경 가림 방지: 단어 뒤에 반투명 박스 또는 글로우. 긴급도 색상(녹→노→빨) 사용 (Typing of the Dead 방식).
화면 중앙·하단 우선: 중요 단어는 시야 중앙에 오도록 카메라 또는 타겟 하이라이트.
레이어 분리: 텍스트는 별도 레이어(깊이 버퍼 무시 또는 항상 위). 3D 오브젝트와 겹침 최소화.
테스트 기준: 저해상도·작은 화면·빠른 움직임에서도 한 눈에 읽히는지. 한글·영어 혼합 시 길이 제한.

(규칙들은 기존 게임 관찰 + Three.js 일반 관행. 정확한 픽셀 값은 추정.)

⑵ 학교 저사양 PC(내장 GPU·크롬북) 60fps Three.js 규칙 7개
인스턴싱·풀링: 단어·적·파티클은 InstancedMesh 또는 Object Pool. 매 프레임 new 금지.
가벼운 머티리얼: MeshBasicMaterial / MeshLambertMaterial. PBR·실시간 그림자 최소화. 그림자 맵 해상도 낮게.
드로우콜 줄이기: 텍스처 아틀라스, 배칭. CSS2DRenderer는 텍스트용으로 제한(DOM 부담 주의).
LOD·거리 컬링: 멀면 단순 모델·텍스트 크기 고정. Frustum culling 활용.
해상도·픽셀 비율 제한: renderer.setPixelRatio(Math.min(window.devicePixelRatio, 1.5)) 또는 고정. 안티앨리어싱 선택적.
애니메이션 단순화: 파티클 수 제한(수백 이하), 셰이더 단순. requestAnimationFrame + 성능 모니터링(stats.js).
초기 로드·메모리: GLTF 압축(Draco/Meshopt), 텍스처 크기 제한(512~1024). 웹워커로 단어 생성 분리 가능.

(Three.js 공식 성능 팁 + 저사양 실무 관행. 정확한 fps는 기기별 테스트 필요.)

⑶ 6종을 3D로 바꿀 때의 장면 아이디어 1줄
디펜스: 탑다운 또는 약간 기울인 3D 성벽·타워에서 다가오는 적 위에 빌보드 단어를 쏴 막기.
퍼즐: 아이소메트릭 종이/블록 세계(Epistory 느낌)에서 단어로 블록 회전·연결·해제.
레이스: 3D 트랙을 달리며 앞에 떠 있는 단어(또는 장애물 위 단어)를 입력해 가속·장애물 제거.
떨어지는 단어 비: 3D 공간에서 위에서 떨어지는 글자 파티클/빌보드를 아래에서 올려다보며 맞추기 (깊이감 활용).
우주 슈팅: TypeSh!t/ZType 스타일 3D 우주에서 다가오는 함선·미사일 위 빌보드 단어를 입력해 요격.
좀비: Typing of the Dead 스타일 온레일 또는 3인칭 시점에서 다가오는 좀비 위 단어 박스.
⑷ 한 종부터 시험할 때 추천

우주 슈팅 또는 떨어지는 단어 비를 추천.

근거: 기존 2D ZType·Word Rain·TypeSh!t처럼 단어가 공간에서 다가오거나 떨어지는 구조가 명확해 빌보드+크기 보정만으로 가독성을 빠르게 검증하기 쉽다. 디펜스·좀비는 카메라 움직임·다수 타겟 관리가 복잡하고, 퍼즐은 상호작용 로직이 무겁다. 레이스는 속도감 연출 부담이 크다. 우주/비는 적은 모델·파티클만으로 60fps 유지하기 쉽고, 타격감(폭발·요격)도 즉시 체감된다. (추정: 저사양에서도 인스턴스드 파티클+빌보드로 충분.)

필요하면 특정 게임 상세 스크린샷 분석이나 Three.js 프로토타입 코드 구조를 이어서 제안할 수 있다.
